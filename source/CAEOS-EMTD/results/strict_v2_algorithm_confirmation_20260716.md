# Strict-v2 初步实验总结与自有算法评估

更新时间：2026-07-17 02:16（Asia/Shanghai，阶段检查点）

## 1. 当前结论

1. 已建立 3 个恶意流量数据集、38 个留一攻击场景、5 个正式种子的 strict-v2 开放集协议。数据集为 Edge-IIoTset（14 场景）、NF-CSE-CIC-IDS2018-v2（14 场景）和 USTC-TFC2016（10 场景）。
2. 自有算法的主要新增点是固定的 `cauchy_modality_support_union` 风险：将已知类校准的 Cauchy 证据与模态支持风险做 Bonferroni 并集。它已在 Edge-IIoT 上通过与开发 seed 完全隔离的四个新种子确认，并完成正式五种子复现。
3. Edge 上的新风险显著改善 AUROC、AUPR 和 OSCR，且不改变已知类 macro-F1。FPR95 均值也改善，但正式五种子 Holm 校正后未显著，不能写成所有指标均显著。
4. NF-CSE 和 USTC 继续使用原冻结策略，因此当前最终 CAEOS 是透明的“套件条件组合策略”，不是一个已经证明可跨所有数据集普适生效的单一新风险函数。
5. 当前仍不能宣称“全面 SOTA”。20 个配对基线的正式矩阵尚未完成，必须等待完整场景级配对统计后再判断。

## 2. 实验协议与完整性

- 正式种子：`7, 11, 19, 23, 37`。
- 开发种子：`7`；算法独立确认种子：`29, 31, 41, 43`；阈值独立确认种子：`47, 53, 59, 61`，三组用途清晰且确认种子无重叠。
- 所有方法共享固定缓存和 train/validation/test split fingerprint。
- 未知类在跨标签指纹清理前隔离；未知或测试标签不参与预处理、模型拟合、风险选择、阈值选择或超参数选择。
- 统计单元为场景：先在场景内平均种子，再对场景做 bootstrap 和配对检验，避免把重复种子伪装成独立样本。

## 6. 部署阈值确认

默认 validation known acceptance `0.95` 在正式 Edge 五种子上的测试 known acceptance 为 `0.928227`，存在部署代价。只使用开发 seed 7，预先固定规则为：“选择使场景均值测试 known acceptance 首次达到 0.95 的最小验证目标”，得到目标 `0.975`。

该目标随后在未参与开发的 `47, 53, 59, 61` 四个种子上确认：

| 项目 | 独立确认结果 |
|---|---:|
| 场景均值测试 known acceptance | 0.971689 |
| 场景块 bootstrap 95% CI | [0.970086, 0.973168] |
| CI 下界是否达到 0.95 | 是 |
| Unknown rejection rate | 0.357929 |
| Unknown F1 | 0.475477 |

因此推荐把 `0.975` 固定为部署 operating point，同时继续用阈值无关的 AUROC/AUPR/FPR95/OSCR 做主算法比较。必须公开其代价：它优先保护已知流量接纳率，会降低未知拒绝率；不能把 operating point 调整描述为排序能力提升。

## 7. 20 个基线与实时进度

## 10. M3S-UPD 状态

M3S-UPD 已完成 strict-v2 runner、矩阵接入、单元测试、合成数据冒烟和真实 Edge-IIoT `Fingerprinting × seed 7` 冒烟。真实冒烟产物包含 metrics、scores、evidence package、model、log、provenance，指纹交叉为 0。

该方法会联合聚类整批无标签测试特征，因此固定标记为 `secondary_transductive`，不进入主归纳式 SOTA 表。3-epoch 真实冒烟 AUROC 为 `0.404197`、AUPR `0.332055`、FPR95 `0.822500`、OSCR `0.317252`、Known macro-F1 `0.676045`。这只能说明实现可运行且短预算效果弱，不能代表论文预算下的最终性能。

结论：暂不启动 190 场景全矩阵。先做 3-5 个代表场景的正式预算复核；若仍明显落后，则保留为次级负结果，避免消耗大量 GPU 时间。

## 11. 还需要完成的实验

### P0：形成可发表的主结论

1. 等待 20 基线正式矩阵全部完成；逐项审计 metrics、scores、provenance、split fingerprint、失败数和重复运行。
2. 用 38 个场景作为独立统计单元，对 CAEOS 与每个基线输出 AUROC、AUPR、FPR95、OSCR、Known macro-F1 的配对差、场景块 bootstrap CI、Wilcoxon 和 Holm 校正。
3. 同时报告全局、逐数据集和逐攻击场景结果；不能只给全局均值，也不能用尚未完成的运行前缀做排名。
4. 固定 CAEOS 代码、策略清单、阈值选择清单和所有哈希，生成最终可复现快照。

### P1：证明自有算法为何有效及是否可泛化

1. 正式消融：Cauchy evidence、modality support、简单并集、Bonferroni 并集、校准前后、去掉各模态支持项；保持模型与切分完全一致。
2. 将新风险在 NF-CSE 和 USTC 上按“开发种子选策略 + 新种子确认”重新评估。若不稳定，应把套件条件策略作为方法设计明确写出，而不是暗示单一风险普适。
3. 鲁棒性：样本上限变化、5%/10%/20% 标签噪声、单模态缺失、特征置乱、数值漂移和跨采集设备/时段变化。
4. 效率：训练时间、推理吞吐、显存、CPU 内存、参数量和风险融合额外开销。
5. 校准与部署：risk-coverage、known acceptance/unknown rejection 曲线、ECE 或 Brier score，并同时报告默认 `0.95` 与确认后 `0.975` operating point。

### P1：扩展恶意流量数据

1. strict-v3 第一批接入服务器上已具备的 NF-UNSW-NB15-v2 和 CIC-IDS2017，先完成标签统一、重复/冲突清理和捕获级或流指纹分组。
2. 第二批扩展 BoT-IoT、ToN-IoT、CICDDoS2019；CICIoT2023 需要先完成 PCAP 特征抽取和捕获级分组。
3. HIKARI2021、DoHBrw2020、Mal_TLS2023 的历史结果必须重新对齐 strict-v3 协议，不能直接与新矩阵拼接。

### P2：补充基线

1. 对 M3S-UPD 先运行正式预算的小型代表场景集，决定是否扩展为完整次级 transductive 表。
2. 再补至少一个近期、面向网络流量的新类检测或未知协议发现方法，减少主表主要由通用 OOD 方法构成的偏差。
3. 对所有非官方适配器明确标注“官方代码”“论文公式复现”或“协议适配实现”；FOSS 尤其不能误写为完整官方代码复现。
