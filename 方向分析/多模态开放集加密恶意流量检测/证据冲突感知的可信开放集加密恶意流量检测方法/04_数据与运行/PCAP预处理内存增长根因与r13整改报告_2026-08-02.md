# PCAP 预处理内存增长根因与 r13 整改报告（2026-08-02）

## 1. 结论

r12 的内存爆炸主因是 16 个长生命周期 TShark 在高基数 DDoS PCAP 上累计 TCP 会话与序列分析状态，而不是 Python 的 `maximum_active_flows`。把匿名 RSS 阈值从 140 GiB提高到 190 GiB不能解决问题，因为 200 GiB cgroup 的硬限制同时计算匿名内存、页缓存和其他内存；现场在匿名内存约 171.5 GB时，另有约 40.6 GB页缓存，总量已经顶到 cgroup 限制。

r13 不以减少包、减少字段、降低每流序列长度或截短既有前缀来换内存。正式方案保持 TShark 原字段语义和 25,000 活跃流上限，只降低并发，并对 Python 载荷状态做输出等价的在线聚合。

同一 RSTFIN PCAP 的 200 万包只读 A/B中，原命令峰值约 1,456,248 KiB；关闭四项 TCP 状态分析后约 623,376 KiB；再加入 TShark session reset 后约 481,576 KiB。该结果证明 TShark 状态是主要内存来源，但不自动证明候选参数可用于正式数据。

## 3. 被拒绝的优化

以下手段未进入正式 r13：

- 不使用 `-c`、显示过滤器或读取过滤器，不减少输入包。
- 不减少 schema 中的任何字段，不降低每流 64 包序列，不缩短 4,096 B payload 前缀或 2,048 B脱敏 L4 前缀。
- 不把活跃流上限从 25,000 降到 12,000；该参数会改变 `active_flow_limit` 分段语义。
- 不关闭额外的 TCP 状态偏好。PARROT 逐字段门禁在第 221 包发现 `frame.protocols`、TLS record 和 TLS handshake 字段变化。
- 正式运行不启用 TShark `-M` session reset。它虽不丢包，但可能改变跨重置边界的状态型协议识别。

因此，候选配置的内存下降不能用来交换内容变化。

## 4. r13 代码整改

### 4.1 Python 有界等价聚合

每个 payload 到达时仍遍历全部字节并精确更新 256 维直方图、payload 总量、方向总量以及长度序列。FlowState 只常驻最终 CSV 所需的 payload/L4 前缀；完整 payload 与脱敏头在聚合后立即释放。真实 1,000 包分片的 r11/r13 part SHA-256均为：

`b369f913677b937a42c6ad854e49cce5e210db767c53478bfd8f2c1b5841c130`

这证明该整改没有改变该真实样本的流记录、序列、统计、payload、标签或分片顺序。

### 4.2 完整处理策略身份

每个 part 新增 `processing_policy` 与 `processing_policy_sha256`，覆盖：

- 流超时、每段最大包数、两个字节前缀长度和活跃流上限；
- TShark 全部已选字段、偏好、session reset 参数与版本；
- packet decoder 身份和预处理源码 SHA-256。

part、合并 CSV manifest 和 completion 均检查该身份。任何旧 part 缺少身份或策略哈希不同都会 fail closed，不能静默复用。

### 4.3 并发与内存门禁

- 200 GiB服务器初始采用 4 个 Python worker + 4 个 TShark。
- 单 TShark RSS 上限为 32 GiB。
- cgroup 总内存 180 GiB触发受控 TERM，190 GiB为绝对上限。
- 每 10 秒记录总内存、匿名 RSS、单 TShark 最大 RSS、CPU和剩余磁盘。
- 可用磁盘低于 500 GiB仍 fail closed。

并发只改变完成时间，不改变任何数据内容。未通过长时资格门前不得恢复 16 路。

## 5. 数据有效性处置

旧 `caeos_unified_multimodal_v3` 的 86 个完整分片来自 r11 的 25,000 活跃流策略，而 r12 启动时将上限改为 12,000且复用条件没有覆盖该参数。缺少逐 part 的 `active_flow_limit=0` 完整证明时，不能认定两种策略等价。因此旧 v3 不得训练、跨数据集测试或写入论文结果。`2026-08-02` 已在确认无进程占用且 r13 只读 v1、写 v4 后，删除旧 v3 的 `_parts` 约 902 GiB；保留约 1.1 MiB 的 `_control` 用于故障审计。

r13 使用全新输出根：

## 6. 验收门禁

r13 当前只是已启动，不等于内存问题已闭环。正式有效需同时满足：

1. 本地和 GPU 端 11 项回归全部通过。
2. 真实 fragment smoke 与 r11 输出 part 哈希完全一致。
3. 最大/最高包数 PCAP 长时运行期间，单 TShark 不超过 32 GiB，总内存不触发 180 GiB受控停止。
4. 至少连续 6 小时无持续失控增长；最后 2 小时增长斜率应低于 1 GiB/h，或能由捕获切换后的内存回落证明有界。
5. `oom`/`oom_kill` 不增加，无 Swap持续换入换出。
6. 全部 part 的处理策略哈希唯一，`active_flow_limit` 计数单独审计并报告。
7. 只有最终 CSV、全行验证、manifest 和 `completion.json` 一致后，才允许写 `ALL_CSV_MATERIALIZED`。
