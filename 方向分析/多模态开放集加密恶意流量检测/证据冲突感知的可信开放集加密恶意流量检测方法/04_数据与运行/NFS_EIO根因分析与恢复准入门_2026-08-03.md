# NFS EIO 根因分析与恢复准入门（2026-08-03）

## 1. 结论

BoT-IoT 标签索引多次发布失败的直接原因不是标签解析、SQLite 构建、内存不足、磁盘容量不足或本地临时盘损坏，而是 `/opt/data/private` 使用了 NFSv3 `soft` 挂载。在 NFS 服务端 `10.32.0.10` 的 WRITE/COMMIT 请求短时无响应后，客户端按照 `timeo=600,retrans=2` 达到重试上限，并把失败作为 `EIO` 返回给 `fsync()` 或 `close()`。

服务端为何在大规模写回阶段不能及时响应，尚不能仅从当前 Pod 内确认。最可能的上游诱因是 NFS 服务或其后端存储在 30 GB 文件连续写入和同步提交时出现延迟尖峰、队列拥塞或短时不可用，需要平台侧结合相同时间点的 NFS 服务端、网络和后端盘阵监控确认。

## 2. 已确认事实

### 2.1 挂载策略

目标路径实际挂载为：

```text
10.32.0.10:/opt/data/default/ZONES/yqwaq/PROJECTS/wangwentong/PRIVATE/wangwt
fstype=nfs, vers=3, proto=tcp, soft, timeo=600, retrans=2,
rsize=1048576, wsize=1048576, fsc, local_lock=none
```

`soft` 的语义是：RPC 请求达到 `retrans` 重试上限后向应用返回 `EIO`。这解释了为何 Python `os.fsync()`、普通 `cp` 的文件关闭以及多轮整文件发布都在约数分钟后失败。

### 2.2 内核证据

GPU 节点内核日志在下列时间重复记录：

```text
2026-08-03 01:51:07 nfs: server 10.32.0.10 not responding, timed out
2026-08-03 03:19:43 nfs: server 10.32.0.10 not responding, timed out
2026-08-03 03:23:31 nfs: server 10.32.0.10 not responding, timed out
2026-08-03 03:27:15 nfs: server 10.32.0.10 not responding, timed out
2026-08-03 03:38:49 nfs: server 10.32.0.10 not responding, timed out
```

日志同时出现 `rpc_check_timeout` 数千次回调被抑制。`/proc/self/mountstats` 的 NFS WRITE 项也存在大量异常重传/超时相关计数，COMMIT 项亦有失败记录。03:19、03:23、03:27 与三次索引发布尝试对应，03:38 与手工 `cp` 发布尝试对应。

### 2.3 数据完整性证据

本地临时盘中的完整索引：

```text
path=/tmp/caeos-label-index-p_7_v3j3/labels.sqlite
size=31,380,746,240 bytes
sha256=82033309ca0450e5a5c0f6ed4cf76d2098ee3bcbbcf9afb0a5c78f3e14df355e
records=73,367,604
PRAGMA quick_check=ok
metadata count matches=true
```

一次 NFS `cp` 虽生成同样大小的 `.partial`，但目标端重读哈希为：

```text
b142ac77e9b7f748bc1839356cbf300cd735c798e1fa29a88fb21643f3fd37ac
```

因此目标文件确实发生内容不一致，不能因为大小相同或 `close()` 之前写入完成就发布。现有 SHA-256 重读门正确阻止了损坏产物进入正式索引。

### 2.4 已排除项

- NFS 容量不足：目标剩余约 4.6 TB，使用率约 55%。
- inode 不足：目标 inode 使用率约 1%。
- 本地临时盘不足：`/tmp` 所在盘剩余约 3.1 TB。
- 内存溢出：构建末期进程常驻内存仅数十 MB，系统可用内存充足。
- 持续网络断开：诊断时到 `10.32.0.10` 的 10 次 ICMP 探测零丢包、平均约 0.38 ms；故障表现为大写回阶段的短时服务不可用，而非持续不可达。
- SQLite 构建损坏：本地暂存库已通过全量 SHA-256、计数、分组计数和 `quick_check`。

## 3. 为何会重复出现

1. 每次发布都要把约 30 GB 数据从本地临时盘写到 NFS。
2. 文件关闭前的 `fsync()` 会要求脏数据完成稳定存储提交，集中触发 NFS WRITE/COMMIT 压力。
3. NFS 服务在压力阶段出现响应超时。
4. 客户端使用 `soft,timeo=600,retrans=2`，达到重试上限即向应用返回 `EIO`。
5. 原发布逻辑把失败作为整文件重试条件，再次写入 30 GB，进一步放大服务端压力，所以相同错误连续出现。

## 4. 当前保护状态

- 已终止遗留的 3 个 `rsync` 进程，停止继续写压 NFS。
- 保留通过验证的 `/tmp` 源索引，不删除、不覆盖。
- NFS 上的 `.partial` 不得改名为正式索引，也不得写入正式清单。
- BoT-IoT 当前状态只能记为 `staging_index_validated_publication_blocked`，不能记为正式完成。
- 在恢复门通过前，不启动 CICDDoS2019 和 DoHBrw2020 的大型索引发布。

## 5. 整改要求

### P0：平台挂载与服务端检查

1. 由存储/Kubernetes 平台管理员把数据完整性路径从 `soft` 改为 `hard` NFS 挂载；优先评估 NFSv4.1/4.2 + TCP。单纯增大 `retrans` 只能延后报错，不能消除服务端停顿或 `soft` 数据完整性风险。
2. 检查 `10.32.0.10` 在上述时间点的 NFS 服务线程、RPC 队列、网卡丢包/重传、后端盘延迟、缓存刷写、控制器错误和导出目录日志。
3. 当前进程位于 Kubernetes Burstable Pod，Pod 内无有效挂载管理 capability，不能在容器内可靠地自行重挂载；必须修改平台卷或节点挂载配置并重建/重挂 Pod。

### P1：恢复验证门

1. 重挂载后记录新的 `findmnt` 输出，必须不含 `soft`。
2. 依次执行 1 GB、4 GB、16 GB、32 GB 的顺序写入、`fsync`、目标端 SHA-256 重读测试；每一级通过后再进入下一级。
3. 测试前后保存 `/proc/self/mountstats` 差分和内核日志；任何 `not responding`、WRITE/COMMIT 超时、`EIO` 或哈希不一致均判失败。
4. 通过 32 GB 门后，再从已验证 `/tmp` 源索引发布 BoT-IoT，发布后重新执行 SHA-256 与 SQLite `quick_check`。

### P2：代码与流程

1. 大型 SQLite 始终在本地 NVMe 临时盘构建和验证，不直接在 NFS 上创建索引。
2. 发布只允许“临时目标 + 完整目标端重读哈希 + 原子改名”；`fsync` 报错时不得仅凭文件大小放行。
3. 失败后保留唯一的已验证源副本，禁止自动整文件无限重试。重试前必须先检查 NFS 健康门。
4. 若平台短期不能更改挂载，可把大产物拆为带独立 SHA-256 的固定大小分块进行暂存，但这只是降低重传成本的临时措施，不能替代 `hard` 挂载和服务端修复。

## 6. 恢复判定

只有同时满足以下条件，才能恢复后续正式预处理：

- 挂载不再使用 `soft`；
- 32 GB 写入/同步/重读哈希门通过；
- 测试窗口无新的 NFS 超时或 EIO；
- BoT-IoT 正式索引与已验证源 SHA-256 一致；
- 正式索引 `quick_check=ok`，记录数仍为 73,367,604；
- 审计文件和总清单明确记录发布方式、源/目标哈希与验证时间。
