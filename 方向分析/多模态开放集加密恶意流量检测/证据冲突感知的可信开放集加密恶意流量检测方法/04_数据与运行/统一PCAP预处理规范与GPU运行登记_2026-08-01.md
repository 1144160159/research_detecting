## 1. 目标与边界

本轮预处理的目标不是立即固定模型输入，而是把原始 PCAP 一次性转换为可追溯、可复用、跨数据集同构的流级基础表。后续实验只能从该基础表选择特征、模态和随机种子，不再重复解析 PCAP。正式数据处理在 GPU 服务器执行；本地仅做代码、单元测试和结果汇总。

“CSV 已材料化”和“标签可用于正式实验”是两个独立门禁。任何数据集只有在 CSV 全行校验、源文件哈希、标签绑定和数据集清单均通过后，才可进入正式训练或跨数据集测试。

## 3. 标准 PCAP 处理方法

1. 输入清单：递归发现直接 PCAP 及 ZIP/TAR/TAR.GZ/TAR.XZ 容器中的 PCAP；对源容器计算 SHA-256，并记录容器成员名、字节数和修改时间。
2. 压缩包处理：ZIP 按成员随机读取；压缩 TAR 只顺序扫描一次，将 PCAP 成员原子暂存，避免每个成员重复解压整个归档。暂存文件仍记录原始容器路径、容器哈希和成员名。
3. 报文解析：正式解码器固定为 TShark 3.6.2，关闭 IP 重组和 TCP 流重组；Python 仅负责流聚合、特征编码、标签和 schema。支持 Ethernet、Linux cooked capture、loopback、裸 IPv4/IPv6，不解密应用层内容。
4. 流构造：以方向无关的规范化五元组构造双向流；30 秒空闲超时或 64 个报文形成一个流段。保留方向序列，避免把正反向统计割裂。
5. 载荷处理：截取每个流段最前 4096 字节传输层 payload，以 Base64 可逆保存；同时对完整流段 payload 计算 256 维字节直方图。无 payload 的 ACK 等报文仍保留头部/时序证据。
6. 时序与头部模态：保存前 64 个报文的长度、微秒级 IAT、方向、IP 协议、TCP flags、payload 长度、TTL 和 TCP window 序列。
7. 隐私与身份：不落盘原始 MAC/IP；端点使用 64 位哈希，保留端口；生成 sample ID、flow key hash、源容器哈希和捕获 ID。
8. 标签处理：路径标签只作为候选。混合捕获必须按五元组/时间与官方真值连接；Edge、CICIDS2017、CIC-ToN-IoT、CICDDoS2019 等需完成 CSV/事件真值交叉核对后才可置为正式标签。

该处理方式遵循加密流量研究中的通行做法：不依赖内容解密，联合使用报文字节、报文序列/时序和流级统计；同时比直接生成模型专用张量更适合后续统一消融和跨数据集测试。

## 5. 并行与资源门禁

- 源文件哈希与 TAR 归档暂存：16 个 I/O 线程。
- 用户分配资源为 32 核 CPU、200 GiB 内存、48 GiB 显存；新端点实测 cgroup v1 内存上限为 200 GiB，GPU 为 RTX A6000（49,140 MiB）。系统虽可见 80 个逻辑 CPU，仍必须按用户给定的 32 核配额调度。
- 200 GiB 档采用 4 个 Python worker 与 4 个 TShark 子进程；并发只改变吞吐，不改变包数、流分段或字段。每 worker 保留原正式语义的 25,000 活跃流和每段 64 包。
- PacketRecord 进入 FlowState 时，对全部 payload 字节在线累计总量与 256 维直方图，只常驻冻结 schema 要求的 4,096 B payload 前缀和 2,048 B 脱敏 L4 前缀；包数、长度、方向和协议序列仍逐项完整保留，不抽样、不删字段。
- 每 10 秒同时读取 cgroup 总内存与匿名 RSS；总内存达到 180 GiB 时受控 TERM，190 GiB 为绝对上限。任一属于本任务进程组的 TShark RSS 超过 32 GiB 时单独触发整组受控停止。
- 资源采样：每 10 秒记录 CPU、匿名 RSS、cgroup 总内存、单 TShark 最大 RSS、运行时长和剩余磁盘。
- 低空间停机：可用空间低于 500 GiB 时发送 TERM 并退出，不继续写满数据盘。
- 互斥：使用 NFS 可用的原子目录锁；该数据盘不支持 `flock`。
- 完成标志：只有 12 个 CSV 全部材料化并通过清单一致性检查后，才写 `ALL_CSV_MATERIALIZED`。该标志不等于全部标签已就绪。

## 6. 验证证据

- 本地回归：11 项通过；GPU 回归：11 项通过。新增门禁明确断言正式 TShark 命令无 `-c`、无显示/读取过滤器、全部原字段存在，并拒绝复用处理策略哈希不同的分片。
- TShark 真实分片冒烟：CICIoT2023 前 1,000 包生成 34 条流段，重复验证非首分片 `offset=1480 bytes`、`L4 header=0`、`payload=328 bytes`，part SHA-256 为 `b369f913677b937a42c6ad854e49cce5e210db767c53478bfd8f2c1b5841c130`。
- r11 首分片独立审计：对 1,000 条前缀记录和 200 条随机记录进行结构、算术、Base64、直方图与全文件 SHA-256 校验，错误数为 0；`BrowserHijacking` 的大类已核验为 `Web_Attack`。
- r11 停机证据：`MEMORY_BUDGET_EXCEEDED anon_rss_bytes=150357430272 threshold_bytes=150323855360`；无 `completion.json` 和 `ALL_CSV_MATERIALIZED`，因此不得将 r11 状态表述为预处理完成。
- r12 启动后连续采样显示匿名 RSS 从 4.49 GiB 增至 14.80 GiB，16 个中断分片合计已重新写入约 17 GiB，且修改时间持续前进；这证明任务在实际解析而非仅保留空闲 PID。
- r12 根因审计：16 个 TShark 合计 RSS 约 153.9 GiB，两个 SYN Flood 进程各约 24--25 GiB，多数 RSTFIN Flood 进程各约 7.6--8.2 GiB，而 Python worker PSS 仅约 44 MiB；后段匿名内存增长约 2.5 GiB/min。190 GiB 匿名 RSS 阈值遗漏约 40.6 GB 页缓存，晚于 200 GiB cgroup 总量限制，故无保护作用。
- 曾验证 `-M` 与关闭 TCP 状态分析的候选配置，但 PARROT 在第 221 包即出现 `frame.protocols` 和 TLS 字段差异，违反“不得改变提取内容”的约束，已从正式 r13 撤回。r13 不使用 session reset、不关闭新增协议状态项。
- r13 真实分片冒烟与 r11 对同一 1,000 包输入生成完全相同的 part SHA-256：`b369f913677b937a42c6ad854e49cce5e210db767c53478bfd8f2c1b5841c130`。
- `packets_skipped_non_ip_or_missing_endpoint` 是非 IP 或缺失端点字段的跳过计数，不属于解析失败；首个 BrowserHijacking 捕获的 59,821 包中有 3,249 包归入该项，与 TShark IP/IPv6 过滤计数完全对应。
