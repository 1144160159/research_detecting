## 1. 权威结论

当前项目**没有形成完整闭环**。准确状态不是“数据、特征、模型和指标均未做”，
而是以下四种完成度被长期混写：

1. 设计或代码存在；
2. 开发缓存和单种子 GPU 实验完成；
3. 同协议候选比较通过；
4. 多种子、外部数据和 95%/5% 安全门正式确认通过。

项目已完成第 1 层的大部分工作和第 2 层的一部分工作，但第 3、4 层尚未完成。
因此当前可以撰写问题、方法、协议、开发结果和负结果，不能宣称工程 95%/5%、
论文多模态终态、全面或选择性 SOTA 已成立。

对五个核心问题的直接回答如下。

| 核对项 | 当前判定 | 直接结论 |
|---|---|---|
| 数据集是否已经确定 | 部分完成 | CICIoT2023 已确定为 PCAP 三模态**开发集**，CICIoT2022 Active 已确定为训练期外部良性；最终确认集、自然流测试集和跨数据集攻击确认集未冻结 |
| 特征是否已经确定 | 部分完成 | 512 字节、16x6 包序列、16 节点包图的缓存合同已冻结；最终特征集合、图模态有效性、特征成本和消融证据未冻结 |
| 预处理是否已经做完 | 部分完成 | PCAP 解析、流切分、定长、硬编码变换、capture-grouped 划分和 known-only 阈值链已跑通；数据质量、去重、全源哈希、自然比例、生产一致性和外部集预处理未闭环 |
| 算法选择流程是否正确 | 不完整 | 研究方向合理，但 `CAEOS-Pairwise` 表格主线与 PCAP 三模态主线没有统一；PCAP 线先上复杂模型、后补同骨干风险基线，缺少完整的单模态和简单融合阶梯 |

## 2. 审计口径

本基准采用四级状态，不再使用含糊的“已完成”。

| 状态 | 定义 |
|---|---|
| `PASS-CONFIRMED` | 冻结协议、正式 GPU、多场景至少五种子、完整哈希、统计和验收门全部通过 |
| `PASS-DEVELOPMENT` | 冻结开发协议和 GPU 结果完整，但只能用于选择或否决候选 |
| `PARTIAL` | 代码、设计或部分结果存在，但缺少关键输入、结果或确认 |
| `FAIL/BLOCKED` | 必需产物不存在，或效果门明确失败 |

证据优先级固定为：不可变协议与 manifest > completion/evaluation > 单任务 metrics >
阶段报告 > 方案文字。只存在脚本、watcher、staging、协议或测试通过，不等于效果完成。

## 4. 问题定义整改

### 4.1 必须冻结的任务

后续 PCAP 主线的样本单位固定为：**由同一源 PCAP 中双向规范化五元组形成的流片段**。
当前实现最多使用前 16 个包，空闲超时 30 秒；该限制必须作为数据和部署合同，而不是
隐藏在提取代码中。

输出固定为两层决策：

1. `alert`：Benign / Malicious；
2. `open_set_label`：Benign / 已知攻击家族 / Unknown。

工程线以低误报告警和已知类型输出为主；论文线必须同时证明已知识别、未知拒识、
多模态贡献、冲突贡献和校准。两条线可以共享模型，但不能用工程二分类结果替代论文
开放集结论。

### 4.2 未知的定义

必须区分：

- `development unknown`：允许用于开发后评价和候选否决，但不得再作为最终确认；
- `confirmation unknown`：协议冻结后才揭盲，类别或数据来源与开发 unknown 不同；
- `domain shift`：新设备、新采集工具或新网络环境，不等同于新攻击类别。

CICIoT2023 的 DDoS、DoS、Mirai 已被反复观察，应全部降级为 development unknown。
最终论文必须增加未参与当前迭代的外部攻击确认集。

## 6. 特征与多模态整改结论

### 6.1 当前特征合同

| 模态 | 当前实现 | 尺寸 | 主要问题 |
|---|---|---:|---|
| 载荷字节 | 流内传输层 payload 拼接，截断到 512 字节，PAD=256 | 512 | 是字节输入，但“语义”能力尚未由对照证明；早期截断可能丢失后段行为 |
| 包行为序列 | 16 包 x 长度、IAT、方向、协议、Flags、载荷长度 | 96 | 定长、硬编码缩放已明确，但截断/重传/乱序敏感性未审计 |
| 包交互图 | 16 包节点 x 5 属性 + 16x16 时序/同向邻接 | 336 | 本质接近包序列链图，节点属性与序列高度重叠，尚未证明图结构提供独立信息 |
| 质量 | payload、包数、边数的覆盖质量 | 3 | 不是完整缺失模态 mask，也没有时间偏差或解析可靠度 |

三种输入的张量合同已经确定，但**最终特征选择没有完成**。同源 PCAP 可以形成合理的
异构表示，但不能仅凭三个编码器名称证明论文级多模态贡献。

### 6.2 特征门 `F0`

必须完成以下同拆分、同种子实验：

1. payload-only Byte-CNN；
2. sequence-only TCN；
3. graph-only GCN；
4. 三模态直接拼接或简单后融合；
5. 证据融合但无冲突项；
6. 完整冲突感知模型；
7. 单模态缺失、污染和随机置换；
8. 链图 GCN 与无图/序列等参数对照。

若图模态相对序列不能稳定提升，必须替换为跨流通信图/端点图，或在论文中降级为
“包关系视图”，不得继续把它作为核心创新。若字节 CNN 不优于字节分布统计，也不得把
“载荷语义”作为已证明贡献。

同时建立特征字典，记录来源、公式、单位、范围、缺失值、线上可用性、计算成本和泄漏
风险。当前 `F0=FAIL`。

## 7. 预处理整改结论

### 7.1 已完成部分

- PCAP 解析支持双向规范化流键；
- 16 包或 30 秒空闲形成流片段；
- 原始地址和端口不进入 payload token；
- 长度/IAT/载荷长度采用固定对数缩放；
- known 内按源 PCAP 分组，train/validation/test capture 交集为零；
- 外层未知家族不进入训练、原型和阈值；
- 告警和拒识阈值只由 known-only validation 或 known-family 伪未知产生。

这些内容证明“开发流水线已跑通”，不能证明“预处理已闭环”。

### 7.2 未完成部分

- 当前协议明确记录 `source_full_pcap_hashes_not_computed=true`；
- 缓存只绑定前缀/缓存 SHA，未绑定全部源 PCAP 内容；
- 每细类最多选择 8 个排序靠前的 PCAP，每 capture 最多 256 个流，不能代表自然流量；
- 未完成 CICIoT2023 流级重复、跨标签冲突和近重复审计；
- 未验证训练和部署解析器逐字节/逐特征一致；
- 未形成可版本化的预处理模型包、输入 schema 和异常处理策略；
- 外部攻击确认集尚无统一适配和标签映射。

### 7.3 预处理门 `P0`

`D0` 通过后，冻结 `preprocess_v1`：源 manifest、split manifest、特征 schema、解析器
SHA、容器/依赖、输出缓存 SHA、重复处理规则和端到端一致性测试必须同时存在。
当前 `P0=FAIL`。

## 8. 算法选择流程整改

### 8.1 当前流程为什么不正确

1. `最新方案.md` 把表格代理多视图的 `CAEOS-Pairwise` 标为论文冻结主算法；
2. 当前 PCAP 主线实际使用 Byte-CNN + Packet-TCN + Packet-Graph-GCN 及另一套风险/告警头；
3. `strict_v4_optimal_self_algorithm/decision.json` 选择 Pairwise，但 `head_to_head=null`，
   本质是挑战者失败后保留 incumbent，不是 PCAP 三模态最终锦标赛；
4. v34 的 MSP/Energy/OpenMax/Mahalanobis++ 共用同一复杂骨干，只比较未知分数，
   不能回答深度三模态骨干是否必要；
5. PCAP 线缺少 XGBoost、单模态网络和简单融合的同协议完整基线；
6. v1-v38 版本过多，新增组件快于数据、特征和最终测试集冻结。

因此算法方向“证据学习 + 冲突 + 开放集风险”可以保留，但当前算法选择流程不能作为
最终选择证据。

### 8.2 正确的选择阶梯

必须在同一 `D0/F0/P0` 合同下按以下顺序执行：

| 层级 | 方法 | 回答的问题 |
|---|---|---|
| B0 | XGBoost/LightGBM 固定摘要 | 深度学习是否必要，已知分类上限在哪里 |
| B1 | payload-only CNN、sequence-only TCN、graph-only GCN | 每个模态是否有独立价值 |
| B2 | 简单拼接、概率平均、简单后融合 | 复杂融合是否必要 |
| B3 | MSP、Energy、OpenMax、Mahalanobis++ | 开放集风险组件是否必要 |
| M1 | 证据融合无冲突 | 证据学习本身的贡献 |
| M2 | 冲突感知完整模型 | 冲突项的净贡献 |
| M3 | 跨家族模态反事实 | 只允许在 M2 冻结后做单变量候选 |
| SOTA | OpenDetect、RoNeTC 等域近邻强基线 | 只在同拆分、同输入资格和完整运行后比较 |

每次只允许改变一个机制；主指标、种子、缓存、拆分、训练预算、阈值和评估器必须相同。
当前跨家族反事实 `v39` 可作为开发候选继续运行，但即使通过 seed 307 成对门，也只说明
值得进入新种子开发，不构成最终算法选择。

## 9. 指标与验收整改

### 9.1 已完善的口径

当前协议已正确区分：

- 已知识别：Known Macro-F1、Balanced Accuracy、逐类 Recall、Benign FPR；
- 未知检测：AUROC-Out、AUPR-Out、`FPR_known@95TPR_unknown`、Unknown-F1；
- 联合开放集：exact OSCR、Known Acceptance、Unknown Rejection；
- 校准：Known-ECE15、Known-Brier、Known-NLL；
- 工程安全：Alert Accuracy/Precision、Attack Recall、Benign FPR、Known type Accuracy、
  Unknown alert Recall；
- 论文完整门：工程六项之外增加 Unknown label Recall。

`Benign FPR` 与开放集曲线 `FPR@95TPR` 已明确区分，这是正确的。

### 9.2 尚未完善的执行

- v38 聚合 evaluation 未输出 ECE、Brier、NLL、Unknown-F1、Acceptance/Rejection；
- PCAP 主线没有至少五种子的均值、标准差、场景块 bootstrap 和配对检验；
- 没有自然业务基率下的每小时误报数；
- 没有 Recall@1%FPR、Recall@5%FPR 的操作曲线；
- 没有特征抽取、单样本/P95/P99 延迟、吞吐、CPU/RAM/GPU 和模型大小；
- 相同 DDoS/DoS/Mirai 测试结果已反复影响人工选型，不能再称最终未触碰测试集；
- legacy OSCR 与 exact OSCR 的历史结果仍共存，最终主表必须统一重算。

因此指标**定义层面基本完善，证据层面未完善**。

## 11. 为什么始终无法闭环

### 11.1 目标和实验对象持续变化

项目同时存在表格 strict-v4、PCAP 三模态、工程双告警、全面 SOTA 和多个自有挑战者。
不同文档分别称 Pairwise、FHMM 或 PCAP 模型为当前主线，没有一个同时绑定数据、特征、
模型、指标和确认集的单一事实源。每条线都做了很多工作，但没有在同一对象上收口。

### 11.2 测试集在研究者层面已被反复使用

代码层面坚持 unknown 不参与训练和阈值，这是正确的；但 DDoS、DoS、Mirai 的测试指标
已被 v1-v38 反复观察并用于下一轮机制设计。人工选择也是模型选择的一部分，因此这些
家族只能视为开发集，不能继续承担最终确认。

### 11.3 数据规模表面足够，独立信息和自然比例不足

19,456 个样本来自 76 个 PCAP，并由每细类最多 8 个 PCAP、每 capture 最多 256 个流
构成。它适合受控开发，但不等于自然业务流；重复会话、设备、时间和攻击事件的独立性
尚未完整量化。95%/5% 是业务目标，却在非自然采样上验收，分母不一致。

### 11.4 三模态存在强同源和特征重叠

序列和图都使用长度、IAT、方向等信息；图主要是 16 包链式邻接。若没有单模态和置换
消融，模型可能只是三次编码相同信号。未知攻击需要跨家族稳定表征，而当前 v38 AUROC
约 0.49，表明风险排序接近随机，问题不在阈值而在表示重叠。

### 11.5 为压低误报采用了过度保守的告警边界

v38 的 Benign FPR 只有 0.65%、Precision 99.96%，但 Attack Recall 只有 58.86%，
Unknown alert Recall 只有 50.72%。这是典型的“高精度、低覆盖”解，而不是接近 95%/5%。
单纯放宽阈值会提高召回并破坏 FPR；更重要的是 AUROC/FPR95 已经证明排序本身很差，
不能靠阈值校准闭环。

### 11.6 基线补在复杂模型之后，无法定位收益来源

当前 PCAP 基线主要是在同一复杂骨干上换未知风险分数。缺少同协议的简单模型、单模态、
简单融合和闭集上限，因此无法判断失败来自数据、特征、骨干、融合、风险还是阈值。

### 11.7 工程完整性长期领先于科学效果

项目有大量 protocol、runner、watcher、audit、manifest 和测试。这些提高了可复现性，
但也容易造成“实现闭环”的错觉。v38 已证明资源和完整性全部通过时，科学效果仍可明确
失败。后续总账必须把 `implementation_ready` 与 `effect_pass` 分栏。

### 11.8 缺少最终外部验证和部署回流

当前没有最终外部攻击确认、自然良性安全、端到端吞吐/误报成本，也没有 unknown pool、
人工复核和新标签回流。开放集模型如果没有回流，只完成了离线拒识，不是业务闭环。

### 阶段 A：单一事实源冻结

2. 新建一个机器可读 `caeos_closure_contract_v1.json`；

通过条件：`D0=PASS`、`P0=PASS`，旧缓存继续保留但标为 development-v1。

### 阶段 C：完成 `F0/B0`

1. 运行 XGBoost 摘要基线；
2. 运行三个单模态模型；
3. 运行简单拼接/后融合；
4. 完成特征与模态消融、污染、缺失和成本分析；
5. 决定图模态保留、替换或降级命名。

通过条件：至少一个多模态模型相对最强单模态在预注册主端点和最差场景上稳定提高，
Known Macro-F1 非劣不超过 0.01，并能解释额外成本。

### 阶段 D：自有算法单变量选择

1. 以简单融合或无冲突证据模型为 base；
2. 单独加入冲突机制；
3. 只有冲突机制通过后，才运行反事实候选；
4. 每个候选先两枚开发种子，均值和最差场景同时过门才扩展；
5. v39 seed 307 仅属于该阶段的现有待完成开发任务。

通过条件：开发门通过后冻结唯一候选，禁止再读取确认集进行结构修改。

### 阶段 E：正式确认

1. 至少五个全新种子；
2. 主数据集已知测试 + 未见外部攻击 unknown + 外部良性自然流；
3. 同协议精简基线与完整消融；
4. 报告均值、标准差、scenario-block bootstrap CI、配对 Wilcoxon、Holm 和效应量；
5. 同时报告三层指标、校准、Recall@1%/5%FPR 和效率。

通过条件：工程六项及其单侧 95% 置信界通过，论文绝对门通过，选择性 SOTA 的预注册
相对端点通过。任一失败只能报告负结果或范围内优势。

### 阶段 F：部署闭环

1. 预处理、模型、阈值和解释整体打包；
2. 测量特征抽取、推理 P50/P95/P99、吞吐和资源；
3. 按自然业务基率计算每小时误报；
4. 建立 unknown candidate pool、人工复核、新类确认、原型/阈值更新和重训练触发；
5. 形成模型卡、监控规则和回滚包。

## 14. 本基准的完成定义

只有以下条件同时满足，项目才可从“开发阶段”升级为“论文与工程闭环”：

- `D0/P0/F0/B0` 全部通过；
- 唯一自有算法在未触碰确认集前冻结；
- 至少五个新种子和外部攻击/良性确认完成；
- 工程 95%/5% 与论文三层指标置信门通过；
- 校准、效率、模态消融、鲁棒性和误差分析完整；
- unknown 候选进入人工复核和数据回流试点；
- 本地文档、代码 SHA、远端 release、协议和结果 manifest 一致。

在此之前，任何“已完成”必须带限定词：设计完成、代码完成、开发实验完成、负结果完成
或确认通过。不得再用其中一种替代另一种。
