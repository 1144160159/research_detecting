# 工程总目标与最优化执行流程

版本：v1.0  
更新日期：2026-07-15  
适用工程：HFT-MGBS

## 1. 工程总目标

在目标服务器、目标链路负载和固定数据协议下，构建一套可持续运行、可降级、可回滚的高速全流量特征抽取系统。系统对所有流量执行固定成本的基础解析，对高价值或高不确定流量按需升级流级、窗口级、多级序列和深层特征，在不突破丢包、P99 延迟、CPU/GPU/内存、队列和关键流覆盖硬约束的前提下，使单位资源获得的有效识别收益最大。

“工程最优”不是单一最高准确率或最高吞吐，而是满足全部硬约束后的 Pareto 最优解。最终方案必须同时回答：

1. 在目标负载下能否持续处理且不丢包；
2. P99/P99.9 是否满足时限，过载时能否有界降级；
3. CPU、GPU、内存和 PCIe 是否留有安全余量；
4. 关键流、稀有流和漂移流是否获得最低保障；
5. 增加的每一类特征是否带来可验证的识别收益；
6. 失败时能否自动回退到基础能力并在规定时间恢复；
7. 代码、配置、数据、特征、模型和结果是否可追踪、可复现。

## 2. 优化对象与系统边界

### 2.1 纳入优化的完整路径

`流量输入 → 捕获/回放 → 最小协议解析 → 流键与方向归一化 → packet/flow/window 基础特征 → 候选优先级 → 自适应预算调度 → sequence/multi-level/deep 特征 → fast/deep 识别 → 指标与反馈`

必须做端到端优化，不能只优化某个模型的推理时间而忽略抓包、解析、流表、内存分配、批处理等待和 GPU 传输。

### 2.2 明确不纳入首轮热路径的内容

- ET-BERT 等完整教师模型只用于离线教师、难例和蒸馏；
- AutoML4ETC 只用于远端离线架构搜索；
- Marina/P4 只作为数据面设计参考，除非具备匹配的 Tofino/bf-sde 环境；
- 论文写作、投稿和新颖性论证不是本工程交付项；
- 本地不保存 PCAP、特征矩阵、模型参数、profiling、日志和运行结果。

## 3. 多目标优化函数

### 3.1 硬约束：任何一项失败即淘汰

设目标负载为 `L_target`，端到端时延预算为 `T_budget`：

| 约束 | 最低要求 |
|---|---|
| 正确性 | 必选特征与 oracle 逐字段一致；窗口、方向、超时、乱序边界测试全部通过 |
| 吞吐 | 稳态可持续吞吐不低于 `L_target`；建议保留不少于 20% 峰值余量 |
| 丢包 | 受控回放在 `L_target` 下因本系统产生的丢包为 0；超过目标负载必须报告首个丢包拐点 |
| 时延 | `P99 ≤ T_budget`；P99.9 和最大等待必须同时报告 |
| 资源 | 稳态 CPU/GPU/显存/内存不超过配置上限，默认目标不高于 85%，为突发和恢复留余量 |
| 调度 | 预算越界次数为 0；所有可选 tier 都有截止时间和有界队列 |
| 保障 | 关键流最低覆盖达到配置门槛，建议初始值不低于 99%；普通高频流不能挤占全部预算 |
| 回退 | GPU/模型/反馈异常时能自动退回 Tier 0/1，捕获线程不等待 GPU |
| 可复现 | 代码哈希、输入哈希、配置、设备、命令、时间、退出状态和结果路径齐全 |
| 本地边界 | 数据、特征、模型、运行产物的本地违规数为 0 |

数值阈值必须在首个远端硬件基线阶段写入 `optimization_profile.yaml`，不能长期保留为口头目标。

### 3.2 软目标：在满足硬约束后排序

候选方案的综合效用定义为：

`Utility = wq·Quality + wk·KeyCoverage + wg·GainPerCost - wl·Latency - wd·DropRisk - wr·ResourceCost - wc·Complexity`

其中：

- `Quality`：macro-F1、balanced accuracy、AUROC/AUPRC、ECE 等任务质量；
- `KeyCoverage`：关键流、稀有类别、漂移流的覆盖；
- `GainPerCost`：相对基础特征新增的质量收益除以 CPU/GPU 时间、内存和等待成本；
- `Latency`：端到端 P99/P99.9，不用平均值代替；
- `DropRisk`：接近过载拐点、队列持续增长或回退失败的风险；
- `ResourceCost`：CPU 周期、GPU 时间、显存、内存、PCIe 和能耗代理；
- `Complexity`：依赖、部署、维护、许可证和回滚复杂度。

权重由应用场景配置，不把不同量纲未经归一化直接相加。最终同时保留 Pareto 前沿和一个部署 champion，避免综合分数掩盖极端短板。

## 4. 推荐的最终工程形态

### Tier 0：不可关闭的全量底座

- 一次最小解析；五元组、方向、包长、时间戳、flags、可见 TLS/QUIC 元数据；
- 固定宽度记录、预分配缓冲、批处理、分片流表；
- 无 GPU 依赖，调度器失效时仍能独立运行。

### Tier 1：高覆盖轻特征与快速识别

- packet/flow/window 增量统计；
- BERT-ps 风格的前 K 个带方向包长、IAT 和 mask；
- FastTraffic 风格紧凑模型或 AutoML4ETC 搜索得到的等预算子网；
- 产出置信度、不确定性、漂移/风险和预计深层收益。

### Tier 2：选择性多粒度升级

- 只处理低置信、关键资产、稀有协议、漂移流和保底探索样本；
- YaTC/UniNet 风格 multi-level 表征与小型 encoder；
- 有界 micro-batch、最大等待和 CPU/Tier 1 回退，不阻塞捕获线程。

### Tier 3：教师与离线优化

- ET-BERT/BERT-ps 完整模型用于教师、难例分析和蒸馏；
- AutoML4ETC 用于精度—参数量—延迟—显存联合搜索；
- 不进入实时全量路径，不把离线最优直接等价为生产最优。

## 5. 最优化执行流程

### G0：目标与环境冻结

**输入**：目标链路、数据来源、服务器、业务时延和关键流定义。  
**动作**：填写优化参数模板；锁定 `L_target`、包长/协议/流型、`T_budget`、资源上限、关键流覆盖、重复次数和随机种子。  
**输出**：版本化 `optimization_profile.yaml`。  
**通过门**：所有必填阈值有明确数值；设备、驱动、Conda、CPU/GPU/NIC/NUMA 记录齐全。  
**失败处理**：不得做“最优”比较，只能做功能烟测。

### G1：组件准入与最小适配

**输入**：850/858 篇论文候选组件清单和本地开源仓库。  
**动作**：核查代码完整度、许可证、依赖、输入输出、可拆组件、预期收益和部署阻塞；按 P0/P1/P2 分级。  
**输出**：组件卡、适配接口、禁用理由；不直接复制许可证不明或强 copyleft 代码。  
**通过门**：每个进入实验的候选都有独立适配层和可替换接口。

### G2：正确性基线

**输入**：远端小型 PCAP、NTLFlowLyzer/BERT-ps/YaTC 参考路径。  
**动作**：验证双向流语义、包长/IAT、flags、窗口、超时、截断、padding、乱序、重传和空载荷。  
**输出**：逐字段差异报告和边界单测。  
**通过门**：必选字段全部一致，容差字段有书面定义；单测和本地禁入检查通过。  
**失败处理**：停止性能和模型比较，先修正数据契约。

### G3：无优化端到端基线

**输入**：固定回放协议和正确实现。  
**动作**：关闭可选优化，分别测捕获、解析、流表、窗口、特征、调度、序列化和模型阶段。  
**输出**：Mpps/Gbps、P50/P95/P99/P99.9、首个丢包点、CPU/GPU/内存/PCIe、火焰图或等价 profiling。  
**通过门**：三次复测，波动处于配置阈值内；原始结果和 manifest 完整。  
**失败处理**：先消除基准噪声，不用不稳定数据指导优化。

### G4：瓶颈排序与单变量优化循环

每轮严格执行：

1. 从 profiling 选出占比最高或最接近硬约束的一个瓶颈；
2. 提出一个可证伪假设和一个主要改动；
3. 保持输入、设备、配置、亲和性和种子不变；
4. 运行正确性回归、性能复测和资源复测；
5. 计算相对收益、置信区间/波动和新增复杂度；
6. 达标则晋升 challenger，不达标则回退并保留失败记录。

推荐优化顺序：

`重复解析/全表扫描 → 对象与内存分配 → 流表分片/锁竞争 → 数据布局与批处理 → CPU SIMD/编译扩展 → GPU micro-batch/传输 → 捕获接口 AF_XDP/DPDK`

不得在没有 profiling 证据时同时重写语言、模型、抓包和调度，否则无法归因。

### G5：等预算特征与模型选择

**输入**：稳定的数据面基线。  
**动作**：在相同前 K 包、可见字节、训练预算、数据划分和 seeds 下比较统计模型、FastTraffic、BERT-ps 小模型、YaTC 小模型、ET-BERT 教师和 AutoML 子网。  
**输出**：质量—P99—吞吐—参数—显存 Pareto 前沿。  
**通过门**：所有比较同时报告质量和资源；教师模型不因精度高而自动进入在线热路径。

### G6：自适应预算调度优化

**输入**：每个 tier 的实测成本、边际收益和系统压力信号。  
**动作**：先静态阈值，再成本/收益排序，再压力反馈，最后将 RL/adaptive-monitoring 作为 challenger；逐步加入关键流保障、探索额度、公平性和迟滞。  
**输出**：预算利用、越界次数、tier 覆盖、关键流覆盖、质量—延迟 Pareto、过载降级/恢复曲线。  
**通过门**：预算越界为 0；关键流保障达标；过载时队列有界，负载恢复后在规定时间恢复 tier。

### G7：真实负载、突发和故障验收

**输入**：IMIX/64B/真实包长，mice/elephant/high-churn，25%—过载阶跃。  
**动作**：测试 GPU OOM/超时、反馈中断、队列满、模型加载失败、数据源中断和进程重启。  
**输出**：首个丢包拐点、长稳曲线、故障回退和恢复报告。  
**通过门**：目标负载全部硬约束通过；建议连续运行不少于 24 小时，最终生产门可提升至 72 小时。

### G8：Champion 冻结与部署

**输入**：Pareto 候选与完整验收证据。  
**动作**：选 champion，保留上一稳定版作为 rollback；冻结代码、配置、模型、特征 schema 和依赖。  
**输出**：版本、哈希、部署包、运行手册、监控告警、回滚命令和验收清单。  
**通过门**：三次正式复测 + 长稳 + 故障注入通过，manifest 状态为 `complete`。

### G9：持续运行与再优化触发

只有以下事件触发新一轮优化：真实负载/协议分布显著变化、质量或 P99 越界、资源余量不足、新候选在同协议下显著优于 champion、依赖/安全问题或硬件变更。新方案始终以 challenger 身份从 G2/G3 开始，不能直接覆盖生产 champion。

## 6. 实验纪律与结果治理

- 实验 ID：`HFT_<stage>_<component>_<load>_<seed>_<timestamp>`；
- 每个正式实验至少一次预热、三次测量，报告单次值和汇总；
- 一次实验只改变一个主变量；批量网格必须记录完整矩阵；
- `metrics.json` 是中间结果，只有存在 `manifest.json` 且 `status=complete` 才算完成；
- 失败实验不删除，记录退出状态、日志路径、失败原因和下一步；
- 原始 PCAP、特征、模型、profiling 和日志只留远端，本地只保留代码、模板和紧凑报告；
- 任何性能结论必须附输入哈希、代码哈希、配置、设备和命令。

## 7. 优化停止条件

同时满足以下条件时停止当前版本优化并冻结：

1. 全部硬约束通过；
2. 最近两轮单变量优化的主要指标提升均低于配置阈值，建议初始设为 3%；
3. Pareto 前沿在三次复测中稳定，没有候选全面支配 champion；
4. 新增复杂度、许可证或运维风险超过可获得收益；
5. 24/72 小时长稳和故障注入通过；
6. 部署、监控、回退和复现材料齐全。

停止只表示当前硬件、负载、数据和目标下的工程最优版本，不表示永久或理论全局最优。
