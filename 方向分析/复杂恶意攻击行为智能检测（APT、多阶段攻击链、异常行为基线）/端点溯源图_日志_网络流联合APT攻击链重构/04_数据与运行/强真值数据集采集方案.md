# 强真值数据集采集方案

- 版本：`collection-v0.1-design`
- 日期：2026-07-15
- 目标：补齐现有公开数据无法提供的端点—日志—网络流精确对齐和完整攻击链真值
- 红线：只在隔离、授权靶场运行攻击仿真；原始数据和模型不落本地

当前准备状态：远端 `datasets/strong_truth/{raw,truth,processed,manifests,quality,splits}` 已建立；manifest、步骤/对齐边 JSON Schema 和标注指南已同步到 `manifests/templates/strong_truth/`。尚未采集任何攻击运行。

## 1. 为什么必须收集

远端现有 LANL comprehensive 同时包含 auth、DNS、flow、proc 和 redteam 锚点，适合多源消融和长时间误报；LANL Unified Host and Network 数据的官方说明也确认主机事件和网络事件的匿名身份可跨源对应。但这些数据没有完整的进程—文件—socket—远端进程攻击链和逐步骤阶段真值，不能单独计算完整链 edge F1。

DARPA Transparent Computing 强调高保真系统 provenance、组件依赖和端到端行为，适合作为端点图与既有攻击调查基线；它也不能自动替代本项目独立三源采集与映射真值。

因此采用三层数据集：

1. **自建 Strong-Truth**：主论文的跨源对齐和完整链真值；
2. **LANL Weak/Scale**：11GB 弱标签主协议与 181GB 规模协议；
3. **DARPA/CICAPT/DIDS 外部数据**：端点或 flow 分支验证，不后验拼接。

官方入口：

- [LANL Cyber Security Research datasets](https://csr.lanl.gov/data/)
- [LANL Unified Host and Network Data Set](https://csr.lanl.gov/data/2017.html)
- [DARPA Transparent Computing](https://www.darpa.mil/research/programs/transparent-computing)
- [MITRE CALDERA](https://github.com/mitre/caldera)
- [Atomic Red Team](https://github.com/redcanaryco/atomic-red-team)

## 2. 数据收集总表

| 优先级 | 数据集/来源 | 动作 | 目的 | 准入结论 |
|---:|---|---|---|---|
| P0 | 自建 Strong-Truth | 新采集 18-24 次攻击运行+良性对照 | 精确对齐边、步骤、阶段和完整链 | **必须** |
| P0 | LANL comprehensive 11GB | 不重复下载；生成 manifest、schema、split 和质量报告 | 多源互补、anchor ranking、FP/host-day | **必须** |
| P1 | LANL unified 181GB | 不重复下载；先抽样审计，核心方法通过后全量 | 规模/效率/证据保持 | 必须但后置 |
| P1 | DARPA TC/OpTC 可获得部分 | 核验来源、许可、schema、ground truth 后再纳入 | provenance 基线和跨场景验证 | 条件纳入 |
| P2 | CICAPT-IIoT2024 | 使用远端现有数据 | flow seed 外部验证 | 可选 |
| P2 | DIDS-MFL | 使用远端现有数据/检查点 | flow encoder/迁移 | 可选 |
| P3 | 其他纯流量 IDS 数据 | 只有出现明确未覆盖流量问题才收集 | 补充 flow 泛化 | 默认不收集 |

“收集更多数据”不等于下载更多网络分类集。首要工作是 Strong-Truth 的跨源时间、实体和攻击步骤真值。

## 3. Strong-Truth 靶场拓扑

最低拓扑：

```text
Attacker / CALDERA server
          |
    isolated switch / virtual network
          |
  +-------+---------+----------------+
  |                 |                |
Windows client   Domain Controller  Linux server
  |                 |                |
Sysmon/Security   AD/Security       auditd/eBPF
  +-----------------+----------------+
          network sensor
       Zeek/Suricata/PCAP
```

建议增加文件/数据库/应用服务器形成跨主机分支。所有节点使用靶场专用账号、IP 和数据，不连接生产网；CALDERA 官方仓库也建议部署在安全隔离环境中而非暴露到互联网。

## 4. 采集源

### Windows

- Sysmon：ProcessCreate、NetworkConnect、FileCreate/Modify、Registry、DNS 等；
- Windows Security：4624/4625/4648/4672、Kerberos/NTLM、对象访问；
- PowerShell Script Block/Module logging；
- 域控/AD 认证与目录服务日志；
- 可选 ETW/EDR 导出，但需记录版本和采样策略。

### Linux

- auditd：execve、文件、权限、账号和网络相关规则；
- eBPF/sysdig/Falco 中至少一种：进程生命周期、文件和 socket；
- auth.log/journald、sudo、SSH、systemd 和应用日志。

### 网络

- Zeek conn/dns/http/ssl/ssh 等可见元数据；
- Suricata eve.json 告警/flow；
- NetFlow/IPFIX；
- PCAP 仅在授权靶场保留，用于 flow 真值复核；
- 交换机镜像/虚拟交换机 tap 的位置和丢包率必须记录。

### 编排与真值

- CALDERA operation/report、agent/ability/adversary 版本；
- Atomic Red Team test GUID、输入参数、开始/结束、退出码和 cleanup；
- 攻击者终端命令历史、控制端日志和截图/人工备注；
- 每个步骤的预期前驱/后继与 ATT&CK technique；
- 攻击前后系统快照和传感器健康。

MITRE ATT&CK 的现有 Data Sources 页面可作为采集覆盖参考，但官方已说明该 Data Sources 体系在 ATT&CK v18 后弃用并转向 Detection Strategies/Analytics；论文必须冻结具体 ATT&CK/STIX 版本，不能依赖滚动 `latest`。

## 5. 攻击场景矩阵

建议 6-8 个场景族，每族 3 次独立运行：

| 场景族 | 必含阶段/行为 | 跨源关键边 |
|---|---|---|
| S1 凭据驱动横向移动 | credential access、remote service、execution | auth/session↔remote host↔flow↔process |
| S2 PowerShell/脚本 C2 | execution、discovery、C2 | command/log↔process↔DNS/flow |
| S3 Web/服务入口到主机 | initial access、execution、persistence | application log↔service process↔file/network |
| S4 持久化后延迟执行 | persistence、delayed execution | registry/systemd/task↔later process |
| S5 文件收集与外传 | collection、archive、exfiltration | file reads↔process↔outbound flow |
| S6 端口转发/代理 | lateral movement、C2 | session/forwarding process↔multiple flows |
| S7 共享账号/NAT 歧义 | valid accounts、remote access | competing identities/flows；对齐困难集 |
| S8 多分支 campaign | discovery、parallel execution、C2/exfil | 一对多阶段/主机分支 |

每个场景覆盖 initial access、execution、credential access、discovery、lateral movement、C2/exfiltration 中至少五个阶段。S7/S8 可作为困难测试族，不进入训练。

## 6. 防止脚本和身份捷径

每次重复运行随机化：

- 主机、账号、IP、端口、工作目录和文件名；
- Atomic/CALDERA 输入参数和合法业务背景；
- 攻击步骤间等待时间；
- 成功/失败步骤和替代路径；
- 攻击工具路径，避免默认 `AtomicRedTeam` 或固定 payload 名称成为标签。

同时保留相同拓扑/业务的纯良性对照和“合法管理员执行相似动作”的 hard-negative run。

## 7. 真值字段

### `steps.jsonl`

```text

start_time_utc, end_time_utc,
source_host, target_host, account, session_id,

```

### `alignment_edges.jsonl`

```text
src_record, dst_record, relation_type,
label=exact|ambiguous|heuristic|unmatched,
candidate_set_id, evidence, annotator_ids, adjudication, notes
```

### `chain.json`

```text
campaign/run, malicious_event_ids, required_edge_ids,
alternative_valid_edges, ordered/partial_order_stages,
optional_context_events, missing_expected_events, truth_notes
```

真值与模型输入物理隔离，攻击步骤、阶段和人工边不得参与候选裁剪或特征生成。

## 8. 单次运行 SOP

1. 冻结 topology、sensor、ATT&CK/CALDERA/Atomic 和代码版本；
2. 时间同步并记录每台主机偏移；
3. 运行传感器自检，写入 `sensor_health.json`；
4. 生成 `run_id`，启动纯良性预热；
5. 启动抓取，记录每源开始时间和文件句柄；
6. 执行攻击步骤，每步记录开始/结束、输入、退出码和异常；
7. 攻击后保留冷却窗和 cleanup；
8. 停止采集，计算文件大小、哈希、事件计数和丢包/缺日志；
9. 将编排日志与各源事件建立候选映射；
10. 两名标注者独立复核关键边，冲突仲裁；
11. 生成 manifest、质量报告和 split 候选；
12. 将 raw 设为只读；后续转换写到 `processed/`，不覆盖原始文件。

## 10. 质量门

| 门 | 阈值/要求 | 不通过动作 |
|---|---|---|
| 文件完整 | 全部文件有大小、SHA-256、开始/结束时间 | 重采或标记不可用 |
| 关键字段解析 | `>=99%` | 修 parser 后重新转换 |
| 时钟 | p95 残差 `<=1s`，否则记录时间区间 | 不允许用窄硬窗口 |
| 网络采集 | 丢包/缺流可量化 | 将健康度传入真值与模型 |
| 对齐真值 | 关键边可 exact/ambiguous 标注 | 不启动完整模型比较 |
| 歧义 | `<=5%` 或保留候选集 | 禁止强制唯一标注 |
| 标注一致性 | `κ>=0.8` | 仲裁并修订指南 |
| 场景覆盖 | 至少5个阶段，含跨主机 | 不能进入主链协议 |
| 重复 | 每族至少3次 | 不做场景级统计主张 |
| 泄漏 | run/host/time/脚本 artifact 审计 | 重做 split/随机化 |

## 11. 数据伦理与安全

- 只使用隔离、授权、可重置的研究环境；
- 禁止在生产网络、公共互联网或未授权设备执行攻击能力；
- 禁止采集真实用户凭据、内容或与研究无关的个人数据；
- 对主机、账号、IP 和命令参数做可逆性受控的匿名化映射；
- 将原始敏感数据、密钥和凭据与研究输出分离；
- 记录许可、保留期、访问控制和删除流程；
- 对外发布前做单独合规/脱敏审查，不因论文复现需求自动公开原始 PCAP 或命令。

## 12. 收集顺序

### 第 1 周：资产与 schema

- 为 LANL 11GB 生成只读 manifest、schema/时间/标签质量报告；
- 冻结 Strong-Truth v0.1 schema、标注指南和传感器清单；
- 完成 1 次良性、1 次最小攻击 dry-run。

### 第 2 周：否证性 pilot

- 采集至少 3 个完整 run；
- 完成 oracle/硬窗口和概率对齐的最小比较；
- 注入偏移/缺源，做 Go/No-Go。

### 第 3-6 周：正式收集

- 逐步达到 18-24 次攻击运行和匹配的良性/hard-negative；
- 每 3-5 次运行做一次质量审计，不等全部收完再发现传感器缺口；
- 完成两个留出攻击族和最终 split 冻结。

### 核心方法通过后

- 才运行 LANL 181GB 全量规模协议；
- 只在 flow 分支需要外部验证时处理 CICAPT/DIDS；
- 不默认继续下载其他单模态数据集。
