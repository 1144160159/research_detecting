Multi-Scenario Cloud–Edge Collaborative DDoS
Detection in LLM-Enabled AIoT
Aoran Huang , Graduate Student Member, IEEE, Jingfu Yan , Xiaojing Fan , and Huachun Zhou

Abstract—DDoS attack detection has become crucial for securing the Internet of Things (IoT). However, next-generation
intelligent networks produce large-scale, heterogeneous data, and
intrusion-detection systems built on conventional AI models lack
the capacity to provide targeted detection for diverse IoT application scenarios. Large language models (LLMs) have attracted
attention due to their strong ability to capture contextual relationships. Given the correlated nature of DDoS flows, using
LLMs for scenario-specific DDoS detection across heterogeneous
IoT applications is a promising direction. Nevertheless, two main
challenges remain: (1) how to enable LLMs to process non-textual
DDoS flow data and to leverage edge models’ detection capabilities
within AI-IoT (AIoT) scenarios; and (2) how to design a detection
framework that harnesses LLM strengths in large-scale, multi-type
data handling to accurately identify diverse attack types across
IoT application scenarios. To this end, we propose CE4LDD, a
cloud–edge collaborative method for detecting DDoS attacks based
on an LLM architecture. We design an order-assignment module, a
token generation group (TGG), and an embedding module for flow
data. DDoS detection is formulated as a token-classification task
within the LLM. During tokenization, we leverage edge models’
detection capabilities. Moreover, to support diverse AIoT scenarios,
we present EAL-BT, a bottom-up training and detection process.
We describe how edge models assist the LLM in scenario-specific
detection and provide CE4LDD’s complete training and detection
workflow. Finally, using CIC2019 and a custom dataset, we simulate
five IoT scenarios under different DDoS attacks. Experimental
results show that the proposed method can help LLM perform
DDoS detection in AIoT and achieve excellent performance in
handling DDoS attacks across different IoT application scenarios.
Index Terms—Large Language Model, AIoT Security, DDoS
Intelligent Intrusion Detection, Multi-Scenario, Intelligent
Network Security.

is a certain correlation between their flow, such as frequent

However, considering the application scenarios of LLM, the
resource distribution of the IoT and the needs of actual DDoS
detection, this paper reviews a large number of recent studies
on DDoS detection in AIoT and the application of LLM in IoT,
mainly facing the following two difficulties:
r Considering the resource constraints at the AIoT edge [38],
LLM can only be deployed in the cloud, while edge models
retain valuable capabilities for detecting prevalent DDoS
attacks. How can these edge models be leveraged to assist
LLM in DDoS detection? Additionally, since LLMs are
designed primarily for textual data—with tokenization,
embedding, and associated processes tailored to natural
language—how can non-textual, unordered flow data be
selected and preprocessed for ingestion by LLM, thus
utilizing its robust capabilities for flow classification [39].
r Edges under the same cloud may serve different application
scenarios [40], and consequently face different types of
DDoS attacks [41]. For example, smart wearable scenarios
and car networking scenarios can be connected to the same
cloud through different edge terminals. However, the main
DDoS attacks on the two are different. How to design
a detection scheme based on the advantages of LLM in
processing large-scale and multi-type data, so that it can
make targeted attack detection for different types of attacks
in different AIoT scenarios.
To address these challenges, this paper first proposes a cloudedge collaboration method based on LLM to detect DDoS attack
flow, named CE4LDD (Cloud Edge for LLM DDoS Detection).
It describes in detail how cloud–edge collaboration processes
flow data according to LLM characteristics, enabling flow classification using the LLM’s capabilities. Its edge function is
provided by the conventional AI model, and the cloud function is
composed of five parts: order generation module, token selection
gating (T-Gate), token generation group (TGG), embedding
module and LLM without mask. Considering the correlation
between DDoS attack flow [42], the module is designed to
give the flow order [43] and generate the flow order matrix.
According to the different types of attacks, the appropriate TGG
is selected by T-Gate based on weight entropy. The TGG is
constructed from aggregated edge models and leverages their
detection capabilities. Compared with the tokenization of text
data, there is no padding tokens added in the process of flow
data tokenization, which is more suitable for LLM to process
large-scale and diversified flow data. The embedding module
maps generated flow tokens into a high-dimensional space for
input to the LLM, enabling analysis of richer high-dimensional
features. We disable the LLM’s masking mechanism so it can
attend to all input flow tokens; DDoS detection is formulated as
a token-classification task within the LLM, and final predictions
are produced by a linear projection layer.
To tailor CE4LDD for AIoT environments and enable scenariospecific DDoS detection, a bottom-up [44] edge assisted LLM
training and detection process called EAL-BT (Edge Assist
LLM-Bottom to Top) is proposed. The architecture can use the
targeted detection ability of the edge model to help the detection
of LLM. For the edge, edge clusters are defined according to the
division of application scenarios. The edge model in each cluster
is trained based on the flow data of the subordinate IoT devices,
so that it has a certain DDoS detection capability. Models in
the same cluster is aggregated into the cloud to construct a
TGG, and the last hidden-layer outputs of these edge models are
combined to generate tokens corresponding to different DDoS

A. Related Work
1) DDoS Detection in AIoT: The development of next generation network technology provides support for ubiquitous
collaboration and connectivity [45], and will also bring more
opportunities for DDoS attacks [46]. The rise of complex application scenarios, such as satellite-terrestrial integrated networks [47], has compelled researchers to account for scenariospecific characteristics. For IoT, different IoT application scenarios and types are vulnerable to different types of DDoS attacks.
Firstly, some work on DDoS attacks in a single IoT scenario or
type is sorted out. X. He et al. [48] et al. simulated the DNS
attack of DrDoS in the ship IoT scenario based on Markov
chain, proved that the IoT in the marine network is vulnerable
to DNS rebinding attacks, and gave the detection and defense
system by controlling access rights. Z. Liu et al. [49] analyzed
the characteristics of LDDoS in SDN-IoT, and designed a double
sliding method with expansion filling to deal with LDDoS flow.
Combined with CNN and LSTM, a detection method of LDDoS

method for LDDoS detection by combining clustering algorithm and decision number to filter traffic features for SDN-IoT
network features. For the application scenario of smart grid,
M.N.Kurt et al. [51] took UDP Flood attack and spam attack in
NetDDoS as the detection objects in this scenario, and proposed
an online privacy-preserving anomaly detection method through
data-driven and differential privacy methods. Z. Tian et al. [52]
analyzed AppDDoS attacks in Web of things and used deep
learning to detect AppDDoS attacks based on various URL
representation methods. Jia. Y [53] used GNN to analyze the
characteristics of DDoS attacks initiated by various applications
and their characteristics for smart home scenarios, and proposed
an improved RCNN user activity inference to help AppDDoS
detection. X. Yan et al. [54] analyzed the enhancement effect
of smart contracts on botnets in the smart blockchain scenario,
and proposed a botnet detection method based on domain embedding and unsupervised learning. W. Ma et al. [55] proposed
a lightweight botnet detection method based on the proposed
cloud-edge-node framework in resource-constrained IoT scenarios. A. Sharma et al. [56] discussed a fundamental component

homomorphic encryption model based on hybrid deep learning

and network attack resistance in the industrial medical Internet of Things scenario. M. F. Saiyedand et al. [58] integrated
CNN and LSTM to detect hybrid DDoS attacks, and optimized

B. Preliminaries
1) LLM for Flow Data: LLM consists of four parts: Tokenization, embedding, LLM backbone and LLM task. The
tokenization part divides the input text, and adds padding token
to cooperate with the mask mechanism in the LLM backbone
to ensure that LLM cannot observe the subsequent input and
ensure the reliability of the model. Embedding is responsible
for vectorizing the generated token and mapping it to a highdimensional space for feature analysis. The LLM skeleton part
is based on multiple Transformers to capture the order and
context correlation between tokens. Its essence is also composed

Finally, perform tasks, including token classification, inference

despite its design for language processing, its ML-based backbone can fundamentally handle non-text flow data. Therefore,
the key to LLM processing flow data is how to design a token
generation module suitable for data to generate flow token and
embedding parts.
The flow is regarded as a language to generate a flow token
after tokenization. Through the context analysis ability of LLM,
the correlation between the front and back flow tokens can be
analyzed and the deep context features can be learned. This is
difficult to achieve by conventional AI models. Conventional
AI often detects attack flow only for the characteristics of a
single flow, such as header characteristics, interval time, etc.
This method ignores the important relationship between flows.
DDoS attacks overwhelm hosts by denying access via voluminous, interrelated flows. After flow tokenization, LLM can not
only mine the deep information between flow tokens, but also
learn the correlation between each flow feature. Therefore, the
analysis method using LLM is more in line with the principle of
DDoS attack. Finally, the DDoS detection task is corresponding
to the token classification task to realize the processing of flow
data by LLM.
The pre-training purpose of Llama3 used in this paper is to
predict the next token. Token classification task is not its native
function, which needs to be realized by adding a linear classification layer to map to the target label space. Therefore, the
same method is used in the flow token classification to achieve
the final DDoS detection. In addition, since the requirement of
DDoS detection does not need to predict the next token, the mask
mechanism blocks the observable range of the subsequent input
flow in order to ensure the feasibility of the prediction. In order to
analyze all the input flow more widely, the mask mechanism is
deleted. The proposed reverse filling mechanism ensures that
the integrity of the LLM architecture will not be destroyed
after the mask removal mechanism, as shown in III B. Considering the difficulty of using a large amount of data to train LLM,
the method proposed in this paper can keep the LLM backbone
unchanged, and the idea of designing only token, embedding
and linear layer modules is reasonable and feasible.

2) DDoS Categories and Correlations: In this paper, DDoS
is divided into five categories: Botnet [11]: Botnet infects a
large number of hosts to form a one-to-many network for bots
to launch attacks. Application layer DDoS (AppDDoS) [89]:
Puppet hosts use the application layer protocol to issue a large
number of requests to the server to exhaust resources. Network
Layer DDoS (NetDDoS) [90]: Depletes resources by repeatedly
sending ACK or SYN packets without responding to a flooding
attack. Low-rate DDoS (LDDoS) [91]: Slow data transmission
prevents the server from interrupting the connection with the
attacking host to exhaust resources. Reflex DDoS (DrDoS) [13]:
Sends a large number of packets to the server by forging packets
and IP addresses to overwhelm the target host. From the above
five principles of DDoS attacks is not difficult to see, DDoS attacks often use duplicate protocols and often go through the same
IP/Port address. This shows that DDoS attacks have similarities
in the direction of flow, source address, destination address,
protocol and other characteristics. Based on this similarity and
combined with the ability of LLM context correlation, DDoS
flow can be better detected. However, the routinely collected
DDoS flow is sorted by default in chronological order. This
sorting method is difficult to reflect the characteristics of DDoS
attacks. Detection in this order weakens the LLM’s attention to
the related rows before and after the flow. In order to enable LLM
to better play its contextual performance, this paper designs
a order assignment module based on the correlation of DDoS
attack flow.

the edge data to the cloud. The order generation module is responsible for sorting the preprocessed flow data according to its
characteristics, giving it order, so as to facilitate the subsequent
LLM analysis of the correlation between flow. T-Gate select the
corresponding TGG by analyzing the type of attack that the flow
data may belong to. The upload model merging module divides
the uploaded model according to the edge server cluster, deletes
the final output layer and averages the output of the last hidden
layer.
The LLM detection part is responsible for classifying the
processed flow to distinguish whether it is DDoS attack flow,
which is composed of TGG, embedding module, LLM without
mask and linear projection layer. TGG is composed of a neural
network model uploaded by the edge server, which is responsible
for tokenizing the flow data and performing high-dimensional
mapping through the embedding module to facilitate input to
LLM for processing. The model in each edge server cluster
deletes the output layer and combines them to form a TGG,
which can be represented as G = {G1 , G2 · · · , GP }, where
Gx ⊆ G. The LLM without mask mechanism is responsible
for processing the data after embedding. Through the maskless mechanism, it focuses on a wider range of flow and pays
attention to the correlation between its flow, so as to facilitate the
token classification task of the tokenized flow token to achieve
the distinction of DDoS attack flow. The linear projection layer
is responsible for the dimensionality reduction mapping of the
high-dimensional data output by the LLM and the final classification result is output.

LLM without mask: The flow data is mapped into highdimensional data by embedding and input into LLM.Since it
remains order and in the form of matrix, considering the characteristics of LLM processing input data, it is input by column. In
LLM, in order to ensure the reliability of the output prediction
results, a mask mechanism is introduced to block all data after
the current input, so as to prevent the input data observed in
advance from affecting the prediction results. However, in the
input process of flow data, the purpose is to analyze the relationship between flow tokens to help detect DDoS flow without
predicting the next flow token. Therefore, the existence of the
mask mechanism affects the LLM ’s analysis of the correlation
between all input flow. In the proposed flow token generation
process, padding tokens are not used to unify the length of the
input flow, but the generated flow matrix is input column by
column to achieve length unification. Therefore, the mask mechanism can be ignored and its batch processing ability and model
performance can not be affected. The way to ignore the mask
mechanism is to directly return the causal mask of the lower
triangle generated in the _prepare_decoder_attention_mask to
None, so as to realize the full connection of attention to observe
all the input flow token, and improve the ability of the model to
analyze the internal relationship of the context flow token.
For the flow data after the order is given, it still maintains its
order after TGG and embedding. In order to enable LLM to pay
attention to the relationship between a wider range of flow and
analyze the order relationship between flows, make full use of
its order, LLM also needs to ignore the mask mechanism. The
LLM ignoring the mask mechanism can focus on all the data
before and after the current input. The improved LLM structure
diagram for flow correlation analysis is shown in Fig. 3.
The improved LLM structure is based on llama3 as the backbone, which consists of flow processing part, backbone part and
classification task part. Flow Processing maps the flow to high
dimensions through the token generation team and embedding
to get X Em input to backbone. After normalization in backbone,
we first analyze the relationship between flow by the attention
mechanism without adding padding token to bypass the mask.

After a series of operations such as merging and normalization,
the feature is input into a MLP for high-dimensional extraction.
After repeatedly passing through the N layer backbone, the
output result is expressed as y Bb = Backbone(X Em ). The
input X Em of the LLM is input by column, and then the flow
token after high-dimensional mapping is classified according
to the idea of token classification in llama3. Finally, enter
the classification task part, perform dimensionality reduction
through the linear layer and output the final classification result
y Class = Class(y Bb ) in combination with the loss function.
The effective part is the first |Fk | term of y Class , and the last
W × V − |Fk | term is the reverse filling of the complete matrix
in order to supplement the order assignment, rather than the
original flow data.
Corresponding the entire flow detection process to the LLM
workflow can better understand how the TGG, the embedding
module, the LLM without mask, and the linear projection layer
work together. The text input in LLM is divided into tokens and
vectorized embedding into the LLM backbone. The proposed
scheme divides the flow order matrix into flow tokens and vectorizes them through the TGG. The TGG is composed of an edge
model with characteristic DDoS attack detection capabilities,
and then the flow token is mapped to a high-dimension through
the embedding module and input into the LLM backbone. The
DDoS detection task is corresponding to the token classification
task in LLM, and the flow token is classified. For the output that
is still in a high-dimensional state after classification, the linear
projection layer is used to project it to low-dimensional to obtain
the final DDoS detection result. During the training process,
the LLM backbone is frozen, and the embedding and linear
projection layers are considered as a whole for joint training.
We exclude the LLM backbone from the training scope because
fine-tuning it requires substantial computational resources, the
available dataset is far smaller than the corpus used during the
LLM’s pretraining, and fine-tuning risks degrading the model’s
pre-trained contextual understanding. Furthermore, fine-tuning
offers limited opportunity to leverage the capabilities of the edge
model.

In order to apply to AIoT scenarios and make targeted detection of different DDoS attacks in different AIoT application
scenarios, this paper presents a bottom-up training and detection
process called EAL-BT. The detection process also includes
two parts: routine detection and supervision detection. Through
EAL-BT, the CE4 LDD in the cloud is assisted by the detection
model in different scenarios of the edge. The complete training
and detection process is shown in Fig. 4, which includes the

for the flow flowing through the cloud and the unconvinced flow
in the edge. Supervised detection is to randomly sample the
credible detection results, combine the detection results of the
edge and the cloud to ensure the detection ability of the model,
and can timely discover the deficiencies and update the model.

B. The Testing Process of EAL-BT
The conventional detection process is shown on the right side
of Fig. 4, including edge detection and cloud detection.
Firstly, the IoT device transmits the flow data flowing through
it to the edge server, and then uses the detection model M
trained by the edge server to perform edge detection and obtain
the detection results. At this time, it can be divided into two
cases: the detection results of the trust edge model and the
detection results of the distrust edge model. It is assumed that
the probability of the model judging the flow as malicious flow
is P , and the probability of normal flow is 1 − P . When one
of them is closer to 1, which means P → 1 or 1 − P → 1, the
test results are more credible. On the contrary, P, 1 − P → 0.5
indicates that the model cannot accurately classify flow. In order
to better reflect the credibility of the detection results, entropy
is used to represent the credibility, which is represented as
HC = −(P log(P ) + (1 − P ) log(1 − P )).
(14)
For P tends to 1 or 0, HC → 0, the credibility of the prediction
results is high; P → 0, the entropy value tends to the maximum
value HC → log(2) and the uncertainty is high. The credibility
threshold is set to τ , for HC < τ , the detection result is credible,
otherwise the HC > τ indicates that the result is not credible.
For trusted results, the detection results are output directly; for
untrusted results, the flow data and results are transmitted to the
cloud together and further detected.
Firstly, the flow data is preprocessed and given the order
to generate the flow order matrix. Through T-Gate, select its
suitable TGG. The flow token is generated by the selected TGG.
Then input it to the LLM without mask by embedding mapping
to high-dimensional and the output result is linearly projected to
obtain the final detection result. For untrusted detection results,
if the detection results in the edge and the cloud are inconsistent,
the detection results in the cloud shall prevail. The inconsistent
results are recorded. Finally, the detection results are returned
to the edge server and the IoT device to complete the entire
detection phase process.
In addition, in order to ensure the reliability of the detection
performance of the detection system, and to update the new attack in time, the supervision and detection process is introduced
to supervise the whole system. In the conventional detection
process, the untrusted detection results are transmitted to the
cloud to improve the credibility. However, for the credible results
that do not need to be transmitted to the cloud, there may still
be detection errors. Therefore, for the detection results that are
judged to be credible, a random sampling method is adopted
to randomly send the flow data to the cloud for detection, and
the detection results of the two are compared. In the case of
consistent detection results, no processing is performed, and
the results of inconsistent detection results are based on the
CE4LDD results in the cloud. In the joint detection stage,
the data whose edge untrusted results are inconsistent with the

detection results in the cloud are collected and all the results
with objections are summarized and recorded. If the number of
recorded objection results exceeds the set threshold τ , it means
that there may be unknown attacks or errors in the system. It is
necessary to retrain the model and update the trained data set to
adapt to new attacks and ensure the reliability of the detection
results.
Latency is a primary concern in cloud–edge collaboration;
therefore, we analyze the testing-process latency T . Detection
latency is decomposed into three components: the edge latency
Te dge, which includes edge-model inference time and gatingmodel computation time; the upload latency Tu pload, which
comprises data upload time and protocol overhead; and the cloud
latency Tc loud, corresponding to the time the LLM requires to
analyze DDoS flows. Consequently, the total detection latency
has two cases. If the edge detection is trusted (i.e.,HC < τ ),
then T = Tedge . If the edge is untrusted (i.e., HC ≥ τ ), then
T = Tedge + Tupload + Tcloud . Thus, the latency of the proposed cloud–edge collaborative architecture is primarily governed by the trust threshold τ , other components are determined
by model and system configurations, such as batch size and GPU
performance.

the same address or request the same protocol can be interrupted
due to the presence of the mask. It is difficult for the model to
learn enough knowledge from the relationship between flows to
detect flow.

VI. CONCLUSION
This paper presents a multi-scenario DDoS detection for AIoT
based on LLM. Firstly, a cloud-edge collaborative method called
CE4LDD is proposed to realize LLM to detect DDoS attacks.
The ability of LLM is utilized by assigning order to flow.
TGG and embedding module are designed to enable LLM to
process non-text type flow data. We formulate DDoS detection
as a token-classification task within the LLM framework; final
decisions are produced by a linear projection layer. Second, we
propose EAL-BT, a bottom-up training and detection process
that enables LLMs to adapt to multi-scenario DDoS attacks
in AIoT and leverages edge-model capabilities to assist cloudbased LLM detection. Public data sets and self-data sets are
used to simulate five scenarios of IoT applications that are
subject to different DDoS attacks. Comparative experiments
are carried out with six models for four different situations:
balanced data, imbalanced data, hybrid attack data and unknown
attack data. The results demonstrate that the proposed scheme
has obvious advantages in detection performance, particularly in
the latter three cases. Through ablation experiments, it is proved
that the designed flow order generation module can improve
the detection performance of DDoS. The designed TGG can
speed up the training of the model. For future work, we will
focus on optimizing transmission latency to improve cloud–edge
adaptability, account for realistic network-traffic characteristics,
and investigate methods for enabling LLM-based detection of
encrypted traffic.
